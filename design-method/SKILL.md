# Design method (generic; written in skill form, not installed as a skill)

Works on an empty project. Product values (sizes, colours, radii) are NOT here: they live in the project's own tokens table, extracted from its approved boards. This package gives the process, the relations the tokens must satisfy, the document set, the agent roles and the scripts.

Package: `SKILL.md` (this file) · `agents/` (one brief template per role) · `scripts/` (checker, budget watcher, install gate: starting points) · `templates/` (document skeletons).

## 1. Process

0. **Palette and design language first.** Before any board, fix the palette by role (accent, text on accent, tint, outline, surface, ink, warning/error) with checked contrast in light and dark, and verify the project has one written down. Decide the design language with the user at the same time, because the boards depend on it. If the platform offers a design-language variant (for example Material 3 Expressive on Android), the user picks or declines it here; it is never added later on top of approved boards. Every colour rule below refers to roles ("the accent"), never to a hue.
0a. **Target first, then phases** (user, 2026-11-09: "dividi fasi… prima prototipo da indicazioni utente e tavole, poi si testa e rifinisce con utente e UX, alla fine test in altre configurazioni… step 0 chiede a user target device, poi 200% carattere, modalità scura"). Step 0 asks the user which device(s) and configurations are the main target. Then three phases, in order:
    - **A. Prototype** from the user's requests and the approved boards.
    - **B. Test and refine with the user and UX on the main target only.** The gate (captures, checker, reviewers) covers only the main-target configurations, for example the Fold open and cover at default font, light mode.
      Phase-B loop, measured 2026-11-09. Wave 11 took 30 min and 94 calls against a 15–20 min target, and its gate was not green. Where the time went, and the rules that follow:
      - **Only a validated capture path in a gate.** Wave 11 used a new capture tool before its equivalence check. Its dumps showed different screen states, giving 48 false deviations, and nobody could tell real from artefact. A new tool runs side by side with the old one first.
      - **Scope is fixed at launch.** Two scope changes reached the owner mid-run (dropping large text, adding a deadline); each cost re-planning and reverts.
      - **One owner within its cap.** A wave planned past 60 calls is split before launch, not cut mid-run.
      - **A new user request supersedes an older rule it contradicts.** The owner updates or removes that rule and its fixture in the same change, and reports it. Asking is not needed when the contradiction is plain (user, 2026-11-09: "dico già io che regola va eliminata, aveva fatto bene, era ovvio").
      - **User rules are protected from agents and reviewers** (case 2026-11-09: the user's "il mese precedente si dovrebbe vedere un po' di più" was encoded as peek ≥24 dp open / ≥16 dp cover. Wave 6 cut it to 8 dp to satisfy a reviewer's alignment finding, rewrote the checker rule to expect 8 dp, and shipped a change marked "pending: the user has not seen it". The user: "è tornato a non vedersi… errore grave nel processo").
        - Only the user changes a rule that comes from their words. A reviewer finding or an agent decision that conflicts with one goes to the user with a screenshot; it is never resolved by editing the rule.
        - Every user rule exists as executable code. Its must-flag fixture encodes the user's own threshold, and its row records the threshold. A self-test fails when the code's threshold or the fixture no longer matches the row.
        - A design change marked "pending: the user has not seen it" blocks install until the user has seen it.
      - **Verify static layout headless first.** The JVM layout tests render every screen in seconds. Device captures are for motion and device-only behaviour, and for the changed screens only (user: "perché 48 catture per modificare dimensioni di 4 testi?").
    - **B2. Final polish with ALL steps** (user, 2026-11-09: "dopo ci sarà polish finale con tutti step prima dell'ultima fase"): the full gate on the main target. That means every screen captured, the board audit element by element, both reviewers, motion recordings, and the unslop/polish pass. It runs once the refine loop has converged.
    - **C. Other configurations, at the end, each with its own checks:** large text (200%), dark mode, reduced motion, screen reader, other sizes and devices.
    No phase-C work, captures or findings during phase B or B2; a phase-C finding that shows up early is recorded for phase C, not fixed.
1. **Boards first.** Before any UI code, draw a static board of each screen and state (normal, empty, partial, error, wide and narrow layout) with the board-designer role. The user approves them. Boards are the spec; a text list of elements is not. Each board has a NOTES file (hierarchy, motion, states, accessibility).
1b. **Platform features, checked against the boards.** After the boards, list the platform features the screens need and verify each where it applies. Examples of what to list: system-bar and inset handling, back navigation behaviour, app icon variants, notifications for long user-visible processes, per-app language, dynamic colour. Record each in the design document's "Platform features" table as enabled and checked (SOURCE or device check) or not applicable with the reason. The Android list (edge-to-edge, predictive back, adaptive icon, promoted notifications and more) is in `platform-notes/android.md`; for another platform write the equivalents.
2. **Extract tokens from the approved boards, as a table, in one place.** Measure every font size and weight by role (page title, subtitle, primary figure, secondary figure, label, caption, card title, chip), every colour by role, radii, paddings, gaps, and the number of accent-filled surfaces per screen. Plain table, no narrative. A role missing from the table is added to the table first, then to code. Use the token-extractor role.
3. **Build only from those tokens, through shared components.** One component per element type (page header, card, card header, row, chip, accent card, figure, attention row). A screen composes components; it never sets sizes, colours, paddings or fonts itself. No raw size literals, no `copy(size * factor)` tuning. If a board draws an element differently from an existing component, build the board's element; do not reuse the nearest one.
4. **Brief from the boards, not from deltas.** A brief for UI work quotes the token table and lists every element of every board it covers. Corrections amend the living spec in place; they are not stacked as lists.
5. **Gate before showing or installing.** Nothing is shown to the user or installed until (a) the algorithmic checker is green and (b) two independent reviewers ran on the same build: a design/consistency reviewer (every screen against its board, hierarchy, colour, alignment, cross-screen consistency) and a UX reviewer (affordances, discoverability, flows, states, targets, copy, motion). Read-only, ranked findings with screenshot evidence. "Looks fine" never overrides a red check; exceptions are recorded with the user's decision.
   Transitions to capture (frames, forward AND back, with the dependent controls in the frames): push, pop, predictive back, list-detail selection, selectors, and every system-driven transition: keyboard show AND hide (the dock or bar that follows it: K22, M8), system-bar changes, fold or size changes. A transition not in the list is not verified.
   Captures come from ONE command, `scripts/capture-all.mjs`, never from a hand-written script, and never from a screen list kept in the tool (every change would need the list redone). In-app capture contract (v2): the app itself (a) lists its destinations from its own navigation model, (b) navigates with no taps, (c) waits for settle, (d) writes its own semantics tree as uiautomator-format XML (taking each node's attributes from the platform accessibility provider, not a re-implementation) and (e) its own screenshot, for every destination and config in one run, then (f) logs DONE; the script pulls the folder once. Real-finger motion sets stay adb-driven. Contract for the app, step by step: a capture hook that that (a) lists its destinations from its own navigation model (the Route type; classes with arguments expand from the synthetic data; an unmapped class fails the run), (b) navigates to one by intent without taps and logs a "settled" line when drawing stopped, honoured only on synthetic data, and (c) tags swipeable strips (`viewportTag`) so rest, drag, hold and mid captures are discovered from each dump. Without the hook: `--crawl` (tap clickables breadth-first, dedupe screens by structure, skip destructive labels). A section: `--only <glob>`.
6. **The check is an algorithm.** The rules run as code on every build (layout tests) and on device dumps (tagged accessibility trees): geometry from bounds, structure from tags and text, source from grep or unit tests. Installs go only through a script that refuses when the check fails.
   - **Every remark that can be code becomes code, in two places at once.** Add it as a rule in the project's checker instance and, in generic config-driven form, in this package's `scripts/`, with its criterion in §2.
   - Telling reviewers or agents to "check for X" is never enough. A remark goes only to the reviewers when no algorithm can decide it, and its critique-rules row says why.
   - **What the checker looks for comes from the user, not from agents.** The checker exists because agents are not reliable, so its rules come from the user's critiques (recorded verbatim) and from the generic checks. An agent's own findings never become rules on their own.
   - **Agents may loosen a wrong flag.** An agent that sees a wrong flag may loosen the rule for that element: a filter for that one element, or a narrower rule when the flag is wrong by construction. It lists every loosening, with its reason, in its report.
   - **Only wrong flags are loosened.** A real repetition (the same fact shown twice on one screen) is fixed in the UI, never filtered. A filter's reason says why the two texts are not the same fact. Judge by meaning: figures that coincide only in synthetic data (a total and its single part, nested windows) are different facts.
   - **Same concept, same code** (user, 2026-11-09: "sono la stessa cosa e stessa classe come fanno a essere diverse, evita che stessi concetti abbiano codice diverso"). One implementation per concept (a period strip, a title, a gesture's haptic, a header); screens pass parameters, never re-implement. The project keeps a concept → owning component list and a source-rule check that fails on a second implementation, plus a behavioural check that the same input gives the same result on every instance.
   - **Every rule is written for its class, by the agent, unasked** (user, 2026-11-09: "non devo dirti io che deve essere generico, devi ricordarlo da solo, sennò che skill è"). When a remark becomes a rule, state the class (same element / same function / same gesture…), make the check app-agnostic and config-driven, and put the user's case only in the fixtures. A rule that names a screen, a word or a value is incomplete.
   - **Same concept, same wording.** The same element or the same function has the same wording everywhere. The checker groups texts by role (testTag/resource-id) across all screens and configs, reduces them to templates (numbers, dates, amounts and user data become placeholders), and flags any role with more than one template unless the variant is approved in config. In code, one formatter per role. Found by the user, not by the check, on 2026-11-09: that is the failure to prevent.
   - **Recapture only what changed.** The gate merges the previous capture folder with fresh captures of the screens the diff can alter.
   - **Repetition is a single-screen property.** On a multi-pane layout each pane is a page of the single-screen app. Repeats across panes are not flagged. Never remove data from a single-screen page to fix a multi-pane layout.
   - **Filters stay visible.** Every applied filter is listed in each report with its count. The user's concrete cases stay as must-flag fixtures, so a loosening that hides one of them shows up as a failing self-test.
7. **Fix the class, not the instance.** When the user points at one defect, fix every element of that type on every screen through the shared component or token, and add a checker rule so it cannot return. Look at every element of every type in the frame, not only what changed.
   - **The example is not the spec.** The class is named by the user's words ("duplicate element check"), not by the example that prompted them (a date shown three times). A brief or a checker rule states the class. The example becomes one test fixture among several.
   - Before relaying a result, compare its scope with the user's words.
8. **Record every critique as a checkable rule.** Each user remark becomes a row in the critique-rules file: verbatim quote, what it means in the UI, kind (GEOMETRY, STRUCTURE, SOURCE, MOTION/UX), the exact rule, status. Group rules by element type, not by the element last reported.
9. **Read the remark against the picture.** Before acting on a short remark, restate it in one line naming the exact element in the referenced screenshot. If two readings fit, ask.
10. **Audit before "done".** "Done" means a board-versus-app audit, element by element (PRESENT, DIFFERENT, MISSING), no unexplained gap, plus the gate. Tests and build prove it works, not that it matches. Whoever relays a "PASS" compares it to the boards first. DIFFERENT needs a recorded reason; MISSING must be 0.
11. **Decided is decided.** Placement and content fixed by an approved board are not reopened; only what the boards do not cover is discussed (council or research only for those).
12. **Plan before UI code.** Order: record the request verbatim; if a reference is ambiguous, ask; research references and motion principles; decide information architecture and hierarchy; boards for approval; implement through one delegated owner with the approved spec; polish pass; verify on a device with recordings. No patches to the old interface while a new design awaits approval.
12a. **A product that uses an external service reads the whole part of its documentation it depends on, before dependent code** (user, 2026-11-10: "Assicurati che leggi documentazione per tutte banche sennò risuvcede lo stesso per altri"; "metti in skill che se si usano servizi si legge tutta parte documentazione necessaria all'app, non solo pezzi"). List the pages from the docs index or sitemap; mark each needed or not needed (reason for not needed); read every needed page to its end and record its length (a truncated fetch, an excerpt or a model summary is not a read); record what the product must handle for EVERY member the service covers (every bank, market, plan, region), not for the member under test; per-member facts come from the service's live metadata or a sourced, dated pack, never from one member's case in code; re-check when the docs change (date recorded). Manifest `templates/service-docs.json`, checker `scripts/addons/service-docs.mjs` (K27).
12b. **Leaving the app never resets a flow** (user, 2026-11-10; K28). List every flow (steps, waits, forms, sign-ins, syncs) with its state holder outside the screen and, for background, recreation, process death and return through a link, an executed restore test or a named known-lost item with its reason; a flow is not done until its four triggers are covered. Manifest `templates/state-restore.json`, checker `scripts/addons/state-restore.mjs`; a source test runs the same rules in the unit-test run.
12c. **A flow is designed from its person-step count** (user, 2026-11-10; K31). Before any flow (setup, connecting a service, import, payment, permission, sign-in) is designed, the research step produces a flow-effort table: per documented, permitted method, the person steps first time and later (screens seen, things typed, sign-ins, app switches), the actor of each step (person or system), its surface (own UI, third-party page in the app, browser, other app), its kind (sign-in, input, consent, wait, choice), and whether it is hideable (the system can do it) or not. The method with the fewest person steps wins unless a reason is recorded; every hideable step is hidden or carries a reason. The same table records, per sign-in, the provider's documented sign-in for apps (K32), the failures its documentation names with the test that covers each (K33), and the return address the app owns with the place of the pending state (K34). Manifest `templates/flow-steps.json`, checker `scripts/addons/flow-effort.mjs`.
13. **Think about the interaction, not the default widget.** Ask what the most direct interaction is: usually a gesture on the content itself (swipe the chart to change period, tap the label for a calendar). Keep an accessible alternative.
14. **Copy.** Reassurance and explanation belong only in setup/onboarding. Working screens carry short labels, figures and states, and at most a help affordance opening the explanation on demand. Honesty markers (estimated, dated, unknown) are states, not explanations.

## 2. Criteria (relations, not numbers)

**Priority: UX above UI** (user, 2026-11-09: "UX va sopra UI come hierarchy, bisogna chiedersi se allineamento compromette UX"). When a visual rule (alignment, gutters, symmetry) conflicts with understanding or using the interface (discoverability, affordance, legibility, reachability), the UX rule wins. Before applying a visual fix, ask whether it weakens an affordance. Example: a swipe peek narrowed to align card edges hides that the content swipes.

**Every page composes through the shared page scaffold** (user, 2026-11-09: "perché […] Posta fuori da schema comune, vanno usati, anche questo da flaggare"). The scaffold owns the system insets, back, progress, title and the bottom action bar. A page that lays itself out from scratch fails a source rule, and the safe-area check catches text or controls inside the system bars.

**Every action confirms its result** (user, 2026-11-09: "nessuna conferma che è collegato… azioni vanno confermate"). The control shows in progress, done (with the new state), or failed (with a short reason and the next step). An action whose screen does not change is flagged.

Each criterion states how it is checked. Tags are test tags exposed to the accessibility dump (resource-ids); propose new ones as needed.

### Hierarchy
- **H1. One primary figure per screen, and it is the largest text on it.** GEOMETRY: exactly one `primary-figure`; its text height exceeds every other text including the page title; its top is in the upper part of the screen (`figureTopRatio`, e.g. 40 %).
- **H2. Type-scale contrast by ratio.** Primary figure at least about 1.5x the secondary figures and about 2.3x the label; exact ratios from the board tokens. Equal-weight figure rows are forbidden. Check: text-height ratios between `primary-figure`, `secondary-figure`, `stat-label`.
- **H3. Few ranks.** Only the roles in the token table (about 9 sizes in 3 ranks: title, figure, text). SOURCE: every text style used is in the table; no size literals or scale factors outside the token file.
- **H4. Label above figure, figure carries the weight.** Label small and medium weight, figure heavy, caption not larger than the label. Check: height and weight order.
- **H5. Secondary and settings controls never compete with the overview.** Not in the primary position next to the main title. Check: no settings control in the `page-title` row.
- **H6. What the user needs at a glance is prominent without being asked.** What a page is about is the biggest element of its header, in the same component on every page of that kind. An example is the current period on a page that swipes between periods.
  - GEOMETRY: every page of the kind exposes a `period-title` (or the project's equivalent tag);
  - its height is equal on all those pages (±1 dp) and not smaller than any other header text;
  - a page of the kind without it fails.

### Colour
- **C1. One accent-filled surface per screen, and it holds the primary figure.** STRUCTURE: exactly one `accent-card` containing the `primary-figure`; screens without a primary figure have none; never two.
- **C2. Content is quiet.** Cards and rows use the neutral surface with a thin outline on the page background. Tint fills are for selection and a small icon disc only. Check: `card`/`content-row` fill and outline equal the neutral tokens.
- **C3. Warning colour only for a real problem** (over budget, over limit, error), always with icon and text, never colour alone. Check: warning-coloured nodes carry tag `over` and exist only in the matching state.
- **C4. The strongest colour is content, not chrome.** The accent fill belongs to the accent card (and tones the active control); never buttons, banners or chips on content screens. SOURCE: the accent as a background only inside the shared accent-card component.
- **C5. Attention is a fixed, small set of places.** Decide the list once and check that nothing outside it calls attention (badge, dot, filled banner). A quiet attention row is an outlined row with icon, title, one line and chevron, shown only when it applies. STRUCTURE: `attention` tags only in the allowed places.
- **C6. Contrast.** WCAG AA (4.5:1; 3:1 large text) on every surface, light and dark. Check: computed from token pairs in a unit test.

### Consistency
- **K1. Same element type, same characteristics.** Page title, subtitle, card title, section label, chip, figure of the same rank, row, gutter: identical size, weight, colour, position and alignment on every screen. GEOMETRY: group nodes by tag across all dumps, compare heights, insets, left edges (tolerance 1 dp).
- **K2. One fixed page header.** Title one line, subtitle exactly one line (reserved even when empty), a trailing control in the same slot, same height everywhere, first content at the same y. Switching pages never moves or resizes it.
  - Per-line heights (wave 7): above a configured font scale (default 1.3) the spec lets header texts other than the title wrap (subtitle, trailing text, chips), so their box heights are not comparable. There the checker compares height per line (box height / line count, `wrapRoles`, `heuristics.wrapAboveScale`); page title and period title stay one line and keep the box-height comparison, so a wrapping title still flags (K1/K2). Below the threshold nothing changes.
- **K3. Card inner padding equal on all sides.** Title row of fixed height and the same top inset in every card whatever the trailing element; last row ends the same distance above the bottom; left equals right.
- **K4. Alignment lines.** Titles, card edges, edge labels and first text share the same left and right lines; nothing at an arbitrary x. Cards and period labels inside a swiping block are not narrowed: at rest they sit on the same gutter line as every other card; the neighbour peek is the gutter margin (gutter - gap), never a narrowing of the block (user, 2026-11-08: "Ottobre è allineato a caso").
- **K5. Rhythm.** One gutter, one gap between blocks, one radius per element class, owned by a single page scaffold (pages set no horizontal padding).
- **K6. Wide layouts use the width deliberately.** Panes split at the device hinge or equally, both populated, balanced gutters, no orphaned column; do not stretch a narrow layout.
- **K7. Targets and labels.** Every clickable at least the platform minimum (`minTouch`; Android/Material 48 dp, iOS 44 pt) with text or a content description; text centred in its control unless it is a left-aligned row.
- **K9. Working screens carry no explanation sentences.** Labels, figures and states only. Reassurance and explanations live in setup/onboarding or behind a help affordance (§1 step 14).
  - STRUCTURE: on working screens, no text node longer than the configured length (`maxCopy`), none with two or more sentences, and none from a banned-phrase list.
  - SOURCE: the same scan over string resources and UI literals outside setup and help files.
- **K8. Each fact once per pane.** A date, period, amount or label appears in one element of a pane, not as title, subtitle, chip and axis at once. Class exception: identical text in sibling items of one repeated component (one line of a row or list layout) whose owner contexts differ (two pillar columns, two ledger rows) is each item's own attribute, not a repetition; identical contexts, no context or a different alignment still flag. Fixture pair: same date in two columns of different owners (clean) vs the same owner twice (flagged).
  - STRUCTURE: on each screen, flag EVERY duplicate, with no classification of what is repeated and no built-in exclusions: identical text nodes, and any value token (a number with its unit or month word) that appears in more than one node. A range and its own endpoints match.
  - Repetition is judged per single screen. A wide two-pane layout is not checked for repetition (the same text in two panes is not a repetition). This is set by config (`duplicateScreens` / `duplicateScope`, stated in the report), never by filters.
  - A legitimate repetition (for example each list row's own state) gets a filter for that ONE element: screen, tag and text, plus a reason. The filter is added after looking at the flagged element and is never broad.
  - Unicode spaces (U+00A0, U+202F, U+2007) are read as U+0020 in every text match, so a figure joined to its symbol by a no-break space repeats and filters like one with a plain space.
- **K10. A figure and its currency symbol are never split.** STRUCTURE (`currencySplit`): any visible text (text attribute, not description) where a digit and a currency symbol (`currencySymbols`, default € $ £, either order) are joined by a breakable U+0020 space flags; the joiner must be U+00A0 / U+202F, otherwise a wrap can leave the symbol alone on a line (source: wave 7 orchestrator brief after reviewer finding R1-02, not a user quote).
- **K11. Same concept, same code (user, 2026-11-09 ~17:25: "sono al stessa cosa e stessa classe come fanno a essere diverse, evita che stessi concetti abbiano codice diverso").** STRUCTURE (source check). One implementation per concept (a period strip, a page header, a chip, a press, a threshold haptic): a config lists each concept's owner files and implementation signatures (the spring, the gesture detector, the tags, never a function name); a signature outside the owner fails, a thin wrapper that only passes parameters has none. A known second implementation needs a reason and a decision and is removed when gone. `scripts/addons/concept-owners.mjs`.
- **K12. A header shows one date range per period (user, 2026-11-09, on a title "7 ott – 6 nov" over "dati dal 10 ott al 6 nov": "utente cosa capisce").** STRUCTURE. Two date ranges for one period in one header are incomprehensible; the title is the range of the days the figures cover (clamped to the data), with no coverage line. Check: add-on `text-forbid`, `dateRangeOnce` (CR-82); the project fixture is the real 09k Spese dump. A title that is a name ("Novembre") with a coverage line ("dati al 6 nov") is one range and passes.
- **K15. Navigation speed (user, 2026-11-09: "passare da una qualsiasi sezione a sezione Pilastri da sidebar ci mette 1s prima di animare, le altre sono istantanee").** BEHAVIOUR. Every navigation starts its transition within one frame budget, so no heavy work runs on a destination's first composition: read models are computed once per data version off the main thread and handed to the screen, assets/JSON are preloaded at start, a missing value renders quietly until ready. Source check (JVM tests): a per-destination read-model budget on a 20x archive (about 8 ms warm) and a rule flagging, inside composable bodies, un-remembered data read models and JSON/asset/SharedPreferences reads (reviewed exceptions in a file, each with a reason). Device check `scripts/nav-latency.sh`: per destination, reset `gfxinfo framestats`, tap the nav item, report input-to-first-animated-frame (limit 100 ms) and the worst frame; flag any destination above 2x the median of the others. The fast (non-debuggable) build only.
- **K13. Wrong edges, compenetrations, hidden content (user, 2026-11-09: "see how 9 October is cut, there's an invisible left ledge. There, when the animation makes it wobble, you can see the cut. Make sure the skill provides way to see wrong edges, compenetrations, being hidden etc.").** STRUCTURE + MOTION. A dump of visible bounds cannot show a glyph cut by an invisible clip edge (the clipped box looks like a normal, smaller one), and a rest dump cannot show a cut that appears only while a spring overshoots. So the in-app dump also writes, per node, `layout-bounds` (the node's own unclipped box), `scroll-end` on a scroller at its end, optional `alpha`, and flat `hidden-node` elements for texts not visible to the user; the capture tool's `--frames [N:ms]` makes the app write N dumps at fixed intervals after every navigation and month swipe (`<screen>-f00.xml`, `<screen>-sw-f03.xml`, no adb round trip per frame). Add-on `visual-integrity` (generic, config block `visualIntegrity`, runs on every rest dump AND every frame; frames are read by this add-on only): (a) **clip-edge**: a text whose layout box exceeds its visible box by more than tolDp on a side, where the cut is not the screen edge, an edge of a drawn container (`boundaryIds`), a scroller's own top/bottom edge, or inside a declared pager/offscreen page (`allowClipIds`); (b) **overlap**: two unrelated leaf elements (text, small control) whose visible boxes intersect by more than tolDp on both axes, none containing the other (generalises CR-69, CR-74, CR-79, which stay as fixtures; a merged tall card and content scrolling under a fixed overlay are not leaves); (c) **hidden** (rest only): text with alpha 0, zero size, or inside the window yet not visible, unless declared (`allowHiddenIds`); and, on a scroller at its end (`scroll-end` or a dump named `*-end`), text under a fixed overlay (`floatingIds`, the dock): the last content must be reachable. Frame rows of one screen merge into one row with the frame count. Fixtures (`viFixtures` in the add-on, run by both self-tests): must-flag the clipped first glyph at rest and as a wobble frame, an overlap, alpha 0 / zero size / clipped-away text, last row under the dock; must-pass a declared peek and a scrolled list above the dock. Loosening a flag needs a per-element reason; the user's case stays a fixture.
- **K14. Aligned to nothing (user, 2026-11-09: "deve flaggare cose non allineate a nulla, sia skill che script"; and "allinea punto di domanda a altezza del titolo").** STRUCTURE. ### Motion and behaviour
- **M1. What belongs together moves together.** Parts of one element (card and its label, row and its chip, pane and its header) share the same transform during movement: same translation, spring and moment. Exceptions are recorded in the spec with the reason. The whole header that names the period of a swiped page (period title, its subtitle, the day chip: everything that describes the period) belongs to that page: in a rest/moving pair each of them is displaced like the current page (same direction, +-1 dp, measured on the page edge that does not touch its clip box), and one present at rest but missing when moving is a capture row, not a pass (`pager-period` add-on, config `periodHeader`). Check: pair dumps (rest, moving) and frames at fixed times.
- **M2. Stable regions stay stable.** A pane that did not change keeps scroll, selection and pixels while another animates.
- **M3. Motion from tokens only.** No spring/tween/duration literals outside the motion token file; reduced motion keeps the state change with a short crossfade. SOURCE: grep.
- **M4. Direct interaction first.** A gesture on the content over a stock widget; always an accessible alternative. Reviewer.
- **M5. One spatial model.** Depth is horizontal: a child enters from the edge while the parent shifts and dims; back is the exact reverse and follows the finger. Springs for space, short tweens only for colour/alpha. Press feedback on pointer down. Haptics sparse, semantic, platform constants. Verify forward AND back, narrow AND wide, quick reversal, at the user's animator scale and at 1.0.
- **M7. A moving element never passes over or under a fixed control (user, 2026-11-09, wave 9 design review H1: a travelling title ran under the back button).** MOTION. Clip a moving header piece to its own slot (the slot starts after the fixed control) or fade it before it reaches the control; never let it overlap. Checked on every rest/moving pair by the add-on `moving-overlap` (CR-79).
- **C-align. Columns of one block put their labels on one line (user review, 2026-11-09, wave 9 M3).** CRITERION. Two figures that share a row have their labels at one y. Checked by the add-on `label-rows` (CR-80); the same wave extends CR-75 (no line starts with the separator) to every label, not only subtitles.
- **M6. Same gesture, same physics (user, 2026-11-09 ~17:05, ~17:10, ~17:35).** MOTION. Captured with a held finger at a short and a long fraction of the page pitch: displacement over travel agrees across strips, and below the commit point it is resisted. Source side: the shared helper is referenced by every such gesture (K11). `scripts/addons/pager-hold.mjs`.
- **M8. One cause, one motion (user, 2026-11-10: "Quando faccio indietro tastiera, i pulsanti sotto commettono 1s a comparire"; "salva in skill quella roba di tastiera e animazioni, è importante"; K22, CR-90).** MOTION. Animations that answer the same cause start in the same frame and share its progress. An element that depends on a driver (the keyboard, the system bars, the fold, a drag, another element) follows the driver's progress or its target instead of waiting for it to end; never start an animation when an animated value reaches its end or crosses a threshold at its last frame. Anti-pattern: a visibility flag derived from the current value of an animated system inset (`WindowInsets.ime.getBottom(...) > 0`) followed by the control's own entrance animation: the flag flips on the last keyboard frame and the control appears about a second late. Correct signal: the driver's animation target or progress (`imeAnimationTarget` / `imeAnimationSource`, `WindowInsetsAnimationCompat.Callback`, or the platform equivalent). ## 3. Starting an empty project

1. Create the document set (section 4) from `templates/`. Write the requests verbatim; research references; choose palette by role and design language with the user; decide information architecture and the hierarchy of each screen (primary, secondary, tertiary) before drawing.
2. Boards for every screen and state (board designer); approval; then the platform-feature list (1b).
3. Token table (token extractor); shared components and page scaffold from it; the tags the criteria need.
4. Checker config and layout tests (checker builder, layout-test owner); adapt `scripts/` (section 6); gate on every build.
5. Implementation owners, one slice each, briefs from the spec rows. Reviewers on the gate. Audit before "done".
6. Keep one living spec per screen (elements per board, amended in place) and one critique-rules file.

## 6. The tools (`scripts/`) and how to adapt them

They are starting points. A project MUST adapt them or they do not help; the project's own copies live in its `tools/` and are derived from these. Every rule added to a project's instance is added here as well, generic and driven by config, in the same change (§1 step 6), so the generic checker always carries every algorithmic criterion of §2.
- **Rule ids belong to the project.** The base prints neutral rule names; the project's own ids (critique-rules.md rows) are added through config `ruleIds`.
- **The base script works for any app.** It holds generic algorithms only: no categories chosen by hand, no language or locale parsing, no project rule ids, no app vocabulary.
- **Specific checks are add-ons.** Anything specific to a language, a domain or an app is a separate add-on check that a project switches on in its config (for example date-range matching for a locale).
- **Exemptions are data.** Legitimate exceptions to a base check are per-element filters in a data file, each with its reason.
- When a remark arrives, decide first which layer it belongs to: base, add-on or filter. Do this against the whole scope (this package and every project using it), not only the last instruction.

| Script | Generic | Adapt per project |
|---|---|---|
| `consistency-check.mjs` + `consistency.config.example.json` | Reads tagged dumps through an adapter, groups by rule, expected = most common value, tolerance, exceptions file, report with `scale N,` header and a `Checks skipped` section, generic `singleton` / `heightRatio` / `heightEquals` / `forbidInside` / `alignRules` mechanisms, co-motion pair mode (rest/moving dumps) | Config: `adapter` (uiautomator, json-nodes, or a new file in `adapters/`), `addons` (frame-dock-island, pager-peek, pager-period, hierarchy-opinions, or your own in `addons/`), tag names, `tokens`, `heuristics`, `naming`, `ruleIds` (the project's own ids), `locale`, `wideLayouts`, tolerance; exceptions file (each with the user's decision) |
| `agent-budget-watch.mjs` | Wakes the main session when an agent crosses 60/90/120/150 unique tool calls | Transcript directory of the host; steps; run in the background when agents start |
| `install-gate.sh.template` | Generic steps: tests green, newest dump report newer than the artifact and clean when re-run; platform part (`scripts/platform/android.sh`, ios and desktop stubs): app not foreground, install, verify | Every `<PLACEHOLDER>`: build artifact, test command, dump folder, and the platform part you source |

Adapting the tools: (1) tag every element type in code and expose it to the dump; (2) write the config from the critique rules (each machine rule needs a tag); (3) run on one capture, check that every deviation is a real defect or an exception with a reason; (4) wire the gate; (5) never lower a tolerance or add an exception to turn a check green without the user's decision.

## 7. Orchestration and budget

1. **The main session reports; an orchestrator coordinates.** The main session gives the objective, receives final reports and relays them after comparing them with the spec. Reporting is not verifying.
2. **One task per agent.** A new task is a new agent with a tight brief, never a message to a running one. Parallel agents only on disjoint files; serialize what shares files or the single device/emulator and say why.
3. **Caps as numbers in the brief.** About 60 tool calls or 150k context per slice. At N-10 calls the agent closes the step it is on; at N it writes state to HANDOFF and returns. Never resume a bloated agent; the next slice gets a fresh agent and a compact packet.
4. **Watcher.** Start `agent-budget-watch.mjs` in the background when agents start. On wake: if the agent is near the end let it finish, else have it write the handoff and start a fresh one.
5. **Bounded returns:** PASS/BLOCK, at most N points, evidence paths. No narration, no full diffs.
6. **Compaction only after a handoff:** update HANDOFF/TODO (done with proof, in progress with files and state, agents, next command, open questions), then compact. Do not open new chats to save tokens.
7. **Batch:** one discovery read, one edit batch, one build, one verification. Screenshots at reduced scale, only decisive frames (about 12 per slice); text via accessibility tree first. Logs to a file; show a tail or a grep.
8. **Devices.** One heavy process at a time (build or emulator); check memory headroom first. Real-device installs only through the install gate, never while the user is in the app; do not launch what needs the user (sign-in, unlock) without saying so.
9. **Decide means start.** An actionable request starts in the same turn (agent launched, message sent, or work done). TODO is only for work truly blocked, naming the blocker. Before ending a turn, every "next step" in the reply must already be running.
10. **Approved spec and "done".** Corrections update the spec in one place; "done" is compared item by item to the spec; an agent's PASS counts only for the criteria it was given; a visual spec is extracted to text where agents read.
11. **Model by task.** The small model (Haiku) for work that is bounded, repetitive or waited on: one capture command, checker reruns and count diffs, numeric checks from dumps against named rules, shapes-and-counts recording, research, council debaters, crops for the user. The mid model (Sonnet) for code, tests, rule rows, design and UX judgement, triage and anything read from pictures. The large model only to orchestrate a big wave or for truly hard work. A small-model brief asks questions answerable from named files and tags, gives the output format, caps at about 20 calls and keeps the context under 100k (above it the small model's price is five times higher); never an open "review this". What it returns as BLOCK or UNVERIFIED on a judgement point goes to a mid-model reviewer or the main session, never to another small-model run. At most one of the two gate reviewers is the small model. The main session spot-checks two numbers of every report against the source. A role's first run on a new model is compared with its previous runs (calls, time, errors) and the table in §5 is corrected if it fails.
